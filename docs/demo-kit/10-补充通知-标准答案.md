# 补充通知 · 匿名样例与标准答案（A 侧）

> 对应 10/28–10/31：原通知 + 补充通知对比、变更联动待办、用户确认、日期核对。
> 数据全部为虚构，未使用真实姓名、学校、电话或邮箱。

## 1. 样例文件

| 文件 | 场景 | 预期 |
| --- | --- | --- |
| `06-补充通知1-原通知.txt` | 奖学金申报，原截止 11/10 | 标准模式，3 项材料 |
| `07-补充通知1-补充通知.txt` | 改期到 11/08 + 新增学院推荐表，明确“以此为准” | 直接更新清单，无需确认 |
| `08-补充通知2-原通知.txt` | 社会实践立项，原截止 11/15 | 标准模式，2 项材料 |
| `09-补充通知2-补充通知.txt` | 改期到 11/08 + 推荐意见改安全承诺书，**没写以此为准** | 改期、换材料都要用户确认 |

## 2. 标准答案

### 样例 1：明确“以此为准”

**识别出的变化**

| 类型 | 字段 | 说明 |
| --- | --- | --- |
| changed | deadline | 截止时间由 `2026-11-10 18:00` 变更为 `2026-11-08 18:00` |
| added | material | 新增材料：学院推荐表 |

**受影响待办**

- 更新截止：准备奖学金申请表 → 2026-11-08 18:00
- 更新截止：准备成绩单 → 2026-11-08 18:00
- 更新截止：准备身份证复印件 → 2026-11-08 18:00
- 更新截止：提交材料至行政楼302 → 2026-11-08 18:00
- 新增待办：准备学院推荐表

**确认项**：没有“哪份有效”的歧义（补充通知明确写了“如有不一致，以本通知为准”），但保存前仍要用户点一次“确认更新”。

**应用结果**：用户确认后，截止时间改为 11/08，材料从 3 项变 4 项，待办从 4 条变 5 条；`change_log.before` 保留原截止时间与原材料。

### 样例 2：没写“以此为准”

**识别出的变化**

| 类型 | 字段 | 说明 |
| --- | --- | --- |
| changed | deadline | 截止时间由 `2026-11-15 17:00` 变更为 `2026-11-08 17:00` |
| added | material | 新增材料：团队安全承诺书 |
| removed | material | 不再出现材料：指导老师推荐意见 |

**必须让用户确认的两项**

1. 补充通知未明确说明是否替代原截止时间（原：2026-11-15 17:00，新：2026-11-08 17:00），请确认以哪个为准。
2. 补充通知未明确说明是否取消材料《指导老师推荐意见》，请确认是否还需要提交。

**受影响待办**

- 更新截止：准备实践立项申报表 → 2026-11-08 17:00
- 需确认是否删除待办：准备指导老师推荐意见
- 更新截止：提交纸质材料至行政楼305 → 2026-11-08 17:00
- 新增待办：准备团队安全承诺书

**应用结果**

- 未确认：`applied=false`，只返回预览和待确认项，**不覆盖**用户现有清单。
- 用户确认后：移除推荐意见及其待办，加入安全承诺书及待办，截止时间改为 11/08；`change_log.before` 保留修改前内容。

## 3. 日期核对标准答案（10/30）

固定当前时间 `2026-10-31 10:00`，核对 `2026-11-08 18:00`：

| 字段 | 结果 |
| --- | --- |
| 剩余天数 | 8 天 |
| 星期 | 周日（周末） |
| 风险等级 | low（还剩 8 天） |
| 建议完成时间 | `2026-11-06 18:00`（周五） |
| 建议文案 | 截止日 11月08日 是周日，建议在 11月06日（周五）18:00 前提交，避免周末无人审核 |

工具调用轨迹会写入 Matter 的 `tool_trace`：

```json
[
  {
    "step": 1,
    "tool": "check_date",
    "arguments": {"due_at": "2026-11-08T18:00:00+08:00", "now": "2026-10-31T10:00:00+08:00"},
    "result": {"days_left": 8, "weekday": "周日", "is_weekend": true, "risk_level": "low"}
  }
]
```

## 4. 复现方式（无需 API Key）

```bash
python src/test_compare_date.py
```

预期输出：`88 通过，0 失败`。其中 Function Calling 协议用假客户端验证了“模型发起工具调用 → 工具结果回传 → 模型总结”的完整链路，不需要真实 Key；边界用例覆盖补充通知误删、日期过期、三档模式裁剪与检索。

## 5. 给 B / C 的对接说明

- 对比：调用 `compare_notifications(original_text, supplement_text, original_matter, supplement_matter)`，把返回的 `data.diff` 直接给前端 `m.diff`；`affected_todos` 是字符串数组，可直接渲染。
- 确认：调用 `apply_notice_changes(original_matter, diff, confirmed=False/True)`；未确认时固定 `applied=false`（`requires_user_confirmation=true`），确认后 `matter.change_log.before` 保留旧内容。`requires_confirmation=true` 只表示还需要额外确认“哪份有效”。
- 日期工具：调用 `run_date_check_tool_loop(matter)`；返回 `tool_calls`、`data.date_check`、`data.suggestions`。配好 Key 后自动走真实 Function Calling。
- 真实模型：未配置 Key 时走同一套 `check_date` 工具并生成规则建议；配好 `LLM_*` 后，`_llm_date_tool_loop` 会先让模型发起 `check_date`，再把工具结果回传给模型总结。
