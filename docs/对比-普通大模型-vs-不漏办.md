# 普通大模型对比：豆包 / DeepSeek / Kimi vs 不漏办

> 测试日期：2026-10-29
> 不漏办环境：真实 DeepSeek Flash（`mode=real`，`/health` 正常）
> 对比方式：同一段通知分别输入豆包、DeepSeek、Kimi 和「不漏办」；前三个只做一次普通对话，不使用工具、知识库或结构化约束。
> 目的：不是证明“我们一定更好”，而是找出普通大模型与结构化办事助手的差异，以及我们这次真实输出的问题。

## 1. 测试通知

```text
关于开展2026年校园创新挑战赛的通知

各学院：
请于下周三（11月5日）17:00前完成线上报名。参赛需准备以下材料：1. 项目申报书（需指导老师签字，一式三份）；2. 演示视频（MP4格式，限时3分钟）。请注意：大一新生需额外提交高考成绩单，大二及以上学生需提供上一学年成绩单。请各团队先将电子版申报书发至辅导员邮箱进行初审，初审通过后，方可录制并上传演示视频。若有省级以上获奖证书，请一并扫描上传（选填）。未按时提交者视为弃权。
```

## 2. 四个输出的总体对比

| 维度 | 豆包 | DeepSeek | Kimi | 不漏办（本次真实输出） |
| --- | --- | --- | --- | --- |
| 输出形态 | 自然语言待办 + 材料分组 | 自然语言 checklist | 自然语言分阶段清单 | **Matter JSON + 12 条 todo + source_ref** |
| 截止时间 | 11/5 17:00 | 11/5 17:00 | 11/5 17:00 | **2026-11-05T17:00:00+08:00** |
| 大一/大二成绩单条件 | 明确“二选一” | 明确按年级准备 | 明确按年级准备 | ❌ 两项都标为 `required`，没有 condition |
| 选填获奖证书 | 明确“选填” | 明确“选填” | 明确“选填” | ❌ 标为 `required` |
| 初审 → 视频顺序 | 正确 | 正确 | 正确 | ⚠️ step 依赖正确，但 step_1 是“完成线上报名” |
| 线上报名位置 | 最后一步 | 最后一步 | 最后一步 | ❌ 被排到第 1 步 |
| 原文出处 | 无 | 无 | 无 | ✅ 每条材料/步骤/待办带 `source_ref.quote` |
| 可执行性 | 需要用户自己整理 | 需要用户自己整理 | 需要用户自己整理 | ✅ 材料/步骤/待办有 ID、状态、依赖，可导出 |
| 额外推断 | 基本忠于原文 | 增加“确认团队成员年级” | 增加“组建团队”（原文未写） | 未明显增加原文外步骤 |
| 日期矛盾 | 未指出 | 未指出 | 未指出 | 未指出（我们也没做到） |

**结论先说**：这次对比里，普通大模型在“条件材料、选填识别、步骤顺序”上比我们更接近人类直觉；我们的优势在“结构化、出处、可执行、可保存/导出”。这不是一份只夸自己的对比，下面把我们的问题也列出来。

## 3. 三个普通大模型的输出要点

### 3.1 豆包

- 把材料分成“项目申报书 / 成绩单（按年级二选一）/ 演示视频 / 选填证书”；
- 明确指出“初审通过之后再录制上传”；
- 把线上报名放在最后一步；
- 额外给出“需要我帮你改成打卡表格版吗”的交互建议；
- 没有原文出处，也没有结构化字段。

### 3.2 DeepSeek

- 用 8 个 checkbox 组织任务；
- 明确“确认团队成员年级”，再准备对应成绩单；
- 明确“先发电子版申报书初审，确认通过后再录视频”；
- 建议保存报名成功截图和提交记录；
- 没有原文出处，不能直接变成可勾选清单。

### 3.3 Kimi

- 按“准备 → 初审 → 初审通过后”三段组织；
- 正确写出成绩单按年级二选一、证书选填、视频在初审通过后录制；
- 额外增加“组建团队，确认参赛成员”，这条原文没有明确要求；
- 没有原文出处，不能直接导出/保存为任务。

### 4.4 待办摘要

共 12 条，包括：

- 完成线上报名
- 填写项目申报书 / 请指导老师签字 / 准备一式三份
- 发送电子版申报书至辅导员邮箱初审
- 录制 3 分钟演示视频 / 导出 MP4 / 上传
- 提交高考成绩单 / 提交上一学年成绩单

问题：

- 把“完成线上报名”放在 todo_1；
- 两项成绩单都要求提交；
- 把选填证书也当成必交；
- 因此缺项核对显示 **“还有 5 项材料要准备”**，其中包含不该同时出现的两项成绩单和选填证书。

## 5. 逐项分析

### 5.1 不漏办的优势

1. **结构化**：不是一段文字，而是 Matter JSON，可直接渲染材料/步骤/待办。
2. **可追溯**：每条材料、步骤、待办都能回到原文 `source_ref.quote`；普通模型只能给结论，不能给逐条依据。
3. **可执行**：12 条 todo 带 ID、状态，可勾选、保存、导出；普通模型要用户自己抄成清单。
4. **流程依赖**：step_3 依赖 step_2、step_4 依赖 step_3，正确表达“初审通过后才能录视频”。
5. **可降级**：真实模型失败仍能走 Mock/本地 OCR，普通模型没有工程级兜底。

### 5.2 不漏办本次的不足（必须修）

| 问题 | 影响 | 优先级 |
| --- | --- | --- |
| 条件材料没有 condition 字段 | 大一/大二两项成绩单同时显示为必交 | P0 |
| 选填证书被标为 required | 缺项核对多报一项，违背原文 | P0 |
| 最终报名步骤排到第 1 步 | 用户按顺序执行会先报名后准备材料 | P0 |
| “下周三（11月5日）”没有做星期一致性校验 | 11/5 实际是周四，所有模型都没指出 | P1 |
| 没有把“电子版/纸质版”作为材料属性 | 申报书“一式三份/电子版初审”只落在 todo 文案里 | P1 |

### 5.3 普通模型的不足

1. 没有 `source_ref`，无法逐条核验；
2. 输出是自然语言，不能直接被前端勾选、保存、导出；
3. 可能加入原文没有的任务（如 Kimi 的“组建团队”、DeepSeek 的“确认年级”属于合理推断但非原文明确要求）；
4. 没有工具调用、日期校验、缺项差集、版本历史；
5. 无法保证同样输入的结构稳定。

## 6. 这次对比的结论

- **普通模型更像“会总结的助手”**：读起来顺、顺序和条件通常更符合人类直觉，但不能直接执行、不能逐条溯源。
- **不漏办更像“能落地的清单引擎”**：结构、出处、待办、依赖、导出更强，但这次在条件材料、选填识别、最终步骤顺序上暴露了明显问题。
- **不能把本次输出直接当作演示答案**：在修复上述 P0 问题前，不能声称“不漏办比普通模型更准确”；目前更准确的表述是“不漏办在可执行和可追溯上更强，语义细节仍需优化”。

## 7. 改进任务

| 优先级 | 任务 | 负责人 | 验收 |
