1. 项目概述

问题背景：校园与职场中的"办事通知"以纯文字、截图、PDF 等形式散落在群消息和公告里，关键信息（截止时间、材料清单、办理步骤、审核要求）分散在长文中。人工阅读容易漏材料、看错时间、混淆流程；通用大模型直接回答又容易编造，用户无法核验。

一句话价值：把一段通知变成可勾选、可溯源、可提醒的待办清单。

目标用户：在校学生（奖助学金、竞赛报名、证件办理）、社团/单位内勤（活动立项、经费报销、场地申请）、职场人士（入职材料、资质办理、行政审批）。

本期范围（P1）：文字通知解析、截图识别、文字型 PDF 提取、三档结构化输出、材料清单与缺项核对、查看依据、材料库检索与追问、补充通知对比与变更确认、清单版本/导出、日期核对、会话隔离与删除、清单保存与恢复。 后续规划（P2）：多文件合并解析、复杂条件分支、向量检索/重排、日历同步、多人协作、网页链接抓正文。

1.3 与通用 AI / 传统方案的区别

方案 输出 主要问题
人工读通知 + 自己列清单 个人笔记 / Excel 慢、容易漏材料、看错截止时间、无法追溯原文
通用大模型直接总结 一段自然语言 可能编造、无法勾选、无法核对缺项、无法保存为任务
固定规则模板 固定字段 泛化差，遇到新通知就要改规则，维护成本高
本项目 Matter JSON + 可勾选清单 + 原文出处 + 可调用工具 需要模型/OCR 能力，复杂表格仍有局限，但输出可执行、可核验、可降级

核心差异不是“总结得更漂亮”，而是把通知变成能执行、能核对、能追溯的结构化对象。

  • 学生收到一条奖学金通知：需要知道截止时间、要交哪些材料、交给谁/交到哪、先做什么后做什么。

4.1 模型选型

4.1.1 选型约束

本项目的输入是中文办事通知，输出是字段固定的 Matter JSON，并且要同时满足“可解释、可降级、可演示”。因此模型选型不是单纯比较“谁更聪明”，而是按下面 7 个约束综合取舍：

约束 具体要求 对选型的影响
中文长文本 能稳定理解公文、通知、表格截图里的中文 优先选中文语料充分、中文指令跟随稳定的通用模型
结构化输出 能按指定 JSON 字段输出，不能夹带解释 需要支持 JSON 模式或强 JSON 指令跟随的模型
多模态 截图里可能同时有文字、表格、数字、日期 文本模型与视觉模型分开配置，视觉模型单独选型
时延与成本 单次解析 10–30 秒可接受，演示成本可控 不盲目追求最大参数模型；按任务难度选性价比档位
供应商可用性 比赛现场网络、额度、接口稳定性不可控 团队统一使用 DeepSeek 官方 API，账号/额度/账单集中管理
密钥安全 Key 不能进入前端和公开仓库 Key 只放后端 .env，前端只调后端
可降级 没有 Key 或接口失败时仍能演示 无 Key 走 Mock / 本地 OCR，接口失败有明确错误与兜底

4.1.2 文本模型：团队统一使用 DeepSeek

团队正式 Key 统一使用 DeepSeek 的文本模型，通过环境变量配置：

# 团队正式 Key 使用 DeepSeek
LLM_API_KEY=<your-deepseek-key>
LLM_BASE_URL=https://api.deepseek.com
LLM_MODEL=deepseek-flash

选择 DeepSeek 的理由：

  1. 团队账号统一：一个团队 Key、一个文本模型，额度、账单和调用记录集中管理，避免多人用不同供应商/不同 Key 导致结果不可复现。
  2. 中文通知理解合适：DeepSeek 对中文公文、通知、材料清单这类长文本的指令跟随和语义理解比较稳定，适合“把通知拆成结构化字段”的任务。
  3. 结构化输出可用：使用 response_format={"type": "json_object"} + temperature=0，配合 JSON Schema 和代码字段裁剪，能稳定产出 Matter；默认选 deepseek-flash 做抽取，deepseek-v4-pro 不作为默认，因为抽取任务对延迟和成本更敏感。
  4. 成本可控：按量计费，输入长度受 MAX_TEXT_LENGTH 控制，抽取任务不需要长链推理；相比每次上最大参数模型，更适合比赛演示和反复联调。
  5. 国内访问更稳定：比赛现场网络、代理和跨境延迟不可控，使用国内可访问的 DeepSeek 官方 API，减少现场演示的网络风险。
  6. 接入成本低：DeepSeek 提供标准 Chat Completions 接口，项目现有 SDK 可以直接调用；LLM_BASE_URL / LLM_MODEL 保持配置化是为了本地测试和后续迁移，团队正式环境固定使用 DeepSeek。
  7. 可降级：没有团队 Key 时走离线 Mock；接口失败返回统一错误信封，不会让页面白屏。

为什么不做微调 / 不用本地小模型？

本项目的难点不是“模型知不知道什么是奖学金”，而是“能不能稳定输出指定结构、能不能不编造、能不能和代码规则配合”。微调需要标注数据、训练资源和持续维护，比赛周期内收益不稳定；本地 7B 级模型在中文长通知、JSON 稳定性、工具调用上还需要额外评测和调优。当前方案把“语义理解”交给 DeepSeek，把“结构、判定、降级”交给代码，整体更可控，也符合团队统一使用 DeepSeek 的部署方式。

4.1.3 视觉模型：单独配置，本地 OCR 兜底

截图解析使用独立的视觉模型配置：

# 当前团队 Key 支持图片输入，视觉模型复用同一个 DeepSeek Key
# 如果控制台实际模型名不同，只改 TEAM_LLM_MODEL
TEAM_LLM_API_KEY=<your-deepseek-key>
TEAM_LLM_BASE_URL=https://api.deepseek.com
TEAM_LLM_MODEL=deepseek-flash

当前团队 Key 支持图片输入，视觉模型复用同一个 DeepSeek Key；如果后续额度/模型调整，视觉模型可以单独替换。视觉调用失败时仍自动降级 RapidOCR，不影响文字主流程。

单独配置的原因：

  • 视觉模型与文本模型解耦，便于单独换模型/额度；当前复用同一个 DeepSeek Key；
  • 截图请求更贵、更慢，只在用户上传图片时调用，不拖累文本主流程；
  • 视觉模型不可用时，自动降级到 RapidOCR（onnxruntime） 本地识别，再把文字送入统一抽取管道；
  • 对“字迹模糊、表格错位、数字被切断”等视觉歧义，模型输出 confirmation_needed，让用户确认，而不是猜。

4.1.5 Key 配置、安全与降级

  • Key 只从后端环境变量读取，前端不接触；.env 已被 .gitignore 忽略，仓库只提交 .env.example。
  • 没有 Key 且 LLM_ENABLE_MOCK=1 时，/health 返回 mode=mock：文本走离线 Mock，截图走本地 OCR，保证演示不白屏。
  • 配置团队 DeepSeek Key 后 /health 返回 mode=real，文本与 RAG 走真实模型；视觉模型已配置时截图走真实视觉模型，否则继续走本地 OCR。
  • 开发阶段的个人 Key（非团队 Key）只用于本机联调，没有提交到仓库，也不作为团队验收数据。
  • 真实模型接口失败时，后端返回统一错误信封，不会把异常堆栈或 Key 暴露给前端。
  • 真实模式默认按 IP + 路径限流（普通接口 60 次/分钟、上传 10 次/分钟），避免演示额度被刷爆。

4.2 Prompt 设计

4.2.1 Prompt 的组织方式

Prompt 不是一段“万能提示词”，而是按任务拆成 6 个专用模板，统一放在 src/prompt.py，并同步到 backend/prompt.py：

Prompt 用途 关键约束
SYSTEM_PROMPT 文字通知 → Matter 只抽原文、禁止编造、三档模式、字段互斥、todo 非空
UPDATE_PROMPT 用户操作 → 状态推演 交付动作防误勾、顺序回填、保持 ID 不变
IMAGE_CHECK_RULES 截图识别附加规则 只对“看不清”写 confirmation_needed，不把缺失当模糊
RAG_QA_PROMPT 材料库追问 先查材料再回答、必须附出处、无依据拒答
COMPARE_PROMPT 原通知 vs 补充通知 找改期/增删材料/冲突，拿不准必须让用户确认
DATE_TOOL_SYSTEM_PROMPT 日期工具调用 必须先调用 check_date，再根据工具结果给建议

拆分的好处是：每个 Prompt 只负责一类判断，规则更短、更不容易互相冲突；出问题时也能定位到具体模板，而不是在一段超长 Prompt 里猜。

4.2.2 角色与任务边界

SYSTEM_PROMPT 的第一条不是“尽量提取”，而是只提取原文出现过的内容：

  • 原文明确写出的字段，is_suggestion=false，必须带 source_ref.quote；
  • AI 自己补充的建议，is_suggestion=true，source_ref.quote 可以为空；
  • 原文没有的字段直接省略，禁止输出 null 占位；
  • 原文只有“12月10日前”但没有年份，按缺失处理，不编造年份；
  • “各学院需组织……”这类不属于个人用户的动作，不进入个人 step_list。

这条边界直接对应比赛的“AI 安全与可控性”：用户能看到每条要求的原文依据，没有依据的内容会被标成“系统建议”，而不是伪装成原文。

4.2.3 系统时间注入与相对时间归一化

Prompt 里注入 NOW = {{NOW}}，由服务端在每次请求时写入当前时间（Asia/Shanghai）。模型负责把“下周三前”“月底前”“通知发布后 7 天内”这类相对时间换算成绝对时间，统一输出 ISO 8601（+08:00）。代码层再做一次解析和校验，避免模型输出“下周三”这种前端无法计算的值。

4.2.4 三档模式：模型先判断，代码再重算

Prompt 要求模型输出 detected_features、complexity_score 和 mode，但最终模式不采信模型。服务端在 notification_extractor.py 里做三件事：

  1. 用固定公式重算复杂度：
score = 0.2*has_deadline + 0.1*has_multiple_reminders + 0.2*has_multiple_steps
      + 0.2*has_materials + 0.1*has_review + 0.1*has_dependencies
      + 0.1*has_recurrence + 0.1*has_sub_steps
  1. 按优先级判定：
has_sub_steps / has_review / has_dependencies → complex
score < 0.3 → simple
0.3 ≤ score ≤ 0.6 → standard
score > 0.6 → complex
  1. 取“模型给的 mode”和“公式算出的 mode”中更高的一档，防止模型把复杂通知降级成 simple，导致材料/步骤被裁掉。

这样同一份通知在不同模型、不同温度下，模式判定仍然稳定、可复现。

4.2.5 字段互斥与 enabled_sections

三档模式不是“字段多一点少一点”，而是有明确的互斥表。enforce_mode 会直接删除当前模式不允许的字段：

模式 允许的 enabled_sections 主要保留字段 明确禁止
simple summary, schedule, source title, deadline, reminders, sources materials, step_list, todo_list, warning_list, attachments, location 等
standard summary, schedule, content, steps, materials, source 加 materials, step_list, attachments, key_points recurrence, permissions, audit_log, comments
complex 全部 8 个区块 全部字段 无

另外，simple/standard 的步骤里会删除 sub_step_list、dependencies、parallel、condition、review、owner 等复杂字段；standard 只保留 deadline_risk、missing_material 两类预警。这样前端只渲染 enabled_sections 声明的区块，不会出现“简单通知给一堆空模块”。

4.2.6 ID、命名与依赖规则

  • step_id / material_id / todo_id 必须按顺序编号，例如 step_1、mat_1、todo_1；
  • material_name 必须是 2–10 字的简短名词短语，例如“报名表”“成绩单”，不能把整句话塞进去；
  • step_list 是“阶段”（2–5 个），todo_list 是“阶段里的具体动作”，两者粒度必须分开；
  • 只有原文明确写了“A 完成后才能做 B”，才写 dependencies；没有明确依赖就按并行处理；
  • todo_list 绝对不允许为空，action 必须是完整动宾短语，例如“准备并填写报名表”。

4.2.7 结构化输出的稳定性

Prompt 层和代码层共同保证 JSON 稳定：

  1. Prompt 层：只输出 JSON、不要 Markdown、不要解释；字段名和类型写死；空数组/空对象省略；temperature=0。
  2. 接口层：优先使用 response_format={"type": "json_object"}；供应商不支持时自动去掉该参数重试。
  3. 解析层：去掉 ``json 代码围栏后再json.loads`；解析失败返回可读错误，不把脏数据交给前端。
  4. 校验层：jsonschema 校验 Matter 结构，失败直接报错。
  5. 修补层：_fix_todo_actions 补空 action，_fix_step_titles 补空 title，_rebuild_missing_items 重建缺项，_merge_ai_output 以旧结构为基准合并，模型漏字段不会把原数据冲掉。
  6. 兜底层：模型失败时走 _code_level_fallback，至少保留基础状态联动。

4.2.8 状态推演 Prompt：防止“材料齐了就把提交动作也勾了”

UPDATE_PROMPT 的核心不是“让模型改状态”，而是给状态推演立规矩：

  • 交付动作防误勾：包含“提交/发送/上交/上传/打包/初审/审核/盖章”的动作，即使材料都准备好了，也不能自动标完成，必须用户明确确认；
  • 顺序与并行区分：有明确“先 A 后 B”的依赖，完成 B 时沿链回填 A；并行分支互不影响；
  • ID 不变：禁止重命名或删除业务条目；
  • 只改被提到的材料：用户没说的材料保持原状，不猜；
  • 代码兜底：模型输出漂移时，_sequential_backfill、_code_level_fallback、_fix_todo_actions 继续完成基础联动。

4.2.9 图片 Prompt：只对“看不清”要求确认

IMAGE_CHECK_RULES 明确区分两类情况：

  • 视觉歧义（字迹模糊、纸张皱褶、遮挡、表格错位、数字被切断）→ 写入 confirmation_needed；
  • 原文就没写（只有“12月10日前”没有年份、单位没写全称、材料压根没提）→ 属于缺失，不写 confirmation_needed，也不编造。

这条规则避免把“信息缺失”误报成“识别失败”，也避免模型用确认弹窗掩盖自己没抽到的事实。

4.2.10 RAG / 对比 / 工具调用 Prompt

  • RAG 追问：先检索、再回答；回答必须附“文件名 - 片段ID - 页码”；检索不到就输出“【未找到依据】……”，不允许用外部常识补答。
  • 补充通知对比：明确写“以此为准/原通知作废”时，改期按补充通知处理；没写时，改期、删材料一律要求用户确认；只输出差异，不重复编造原文。
  • 日期工具调用：要求模型先调用 check_date，再根据工具返回的 days_left / is_weekend / suggested_finish_at 生成建议；模型不调用时，代码层仍会执行一次工具，保证“至少有一次真实调用”。
  • 状态更新：只允许改状态和补缺项，不允许改业务字段；模型失败时保留原清单并返回错误。

4.2.11 Prompt 迭代经验

这版 Prompt 不是一次写成的，主要迭代点：

  1. 从“让模型自由总结”改成“固定字段 + JSON Schema”，解决前端无法渲染的问题；
  2. 从“模型自己给 mode”改成“公式重算 + 取更高档”，解决复杂通知被降级；
  3. 从“材料/步骤混在一起”改成“step 是阶段、todo 是动作”，解决清单粒度混乱；
  4. 从“没有依据也硬答”改成“source_ref + is_suggestion + 无依据拒答”，解决幻觉；
  5. 从“改期直接覆盖”改成“差异预览 + 用户确认 + change_log”，解决补充通知误覆盖；
  6. 从“日期让模型算”改成“模型调工具、代码执行”，解决模型算错日期和周末的问题。

4.3 输出稳定性（C 侧实现）

  1. 复杂度重算：不采信模型给的分数，用固定公式 0.2·deadline + 0.1·多提醒 + 0.2·多步骤 + 0.2·材料 + 0.1·审核 + 0.1·依赖 + 0.1·周期 + 0.1·子步骤， 再按 has_sub_steps/has_review/has_dependencies → complex、<0.3 simple、0.3–0.6 standard、>0.6 complex 判定。
  2. 字段裁剪：enforce_mode 按模式删除互斥字段（simple 不出现 materials/step_list/todo_list 等），保证前端渲染契约稳定。
  3. Schema 校验：jsonschema 校验 Matter 结构，失败直接返回可读错误，不把脏数据交给前端。
  4. 三层降级：真实模型 → 本地 OCR（图片）→ 离线 Mock（无 Key），任一层可用即可演示。

4.4 多模态与 OCR（A + C 共同实现）

4.4.1 分工与处理流水线

  • A 侧：analyze_notification_from_image 视觉抽取函数、截图专用 Prompt 规则（表格/人数/日期/材料/金额）、confirmation_needed 判定。
  • C 侧：/api/analyze-image 接口、文件大小/格式校验、本地 RapidOCR 兜底、统一抽取管道。
用户上传截图
  → 格式/大小校验（JPG/PNG/WEBP，≤5MB）
  → 有视觉 Key：视觉模型 + 截图专用 Prompt

4.4.2 截图识别重点

截图与纯文字不同，通知里的关键信息经常以“表格 + 短句 + 数字”混排出现。Prompt 要求优先识别：

类型 例子 输出字段

4.4.3 视觉歧义与“看不清”规则

IMAGE_CHECK_RULES 只把视觉歧义写入 confirmation_needed：

  • 字迹模糊、纸张皱褶、遮挡、反光；
  • 表格错位、数字被切断、日期只有两位数年份；
  • 同一字段出现两个互相冲突的值。

以下情况不写 confirmation_needed，而是按“原文没写”处理：只写“12月10日前”没有年份、单位没写全称、材料压根没提。这样避免把“信息缺失”误报成“识别失败”，也避免模型用确认弹窗掩盖漏抽。

4.4.4 PDF 处理与边界

POST /api/analyze-pdf 接收 ≤10MB、≤30 页的文字型 PDF，用 pypdf / pymupdf 提取逐页文字，再走统一抽取。扫描版提取不到文字时明确返回“请改用清晰截图或直接粘贴文字”，不返回空 Matter。PDF 的页码会保留在片段元数据里，方便 RAG 引用时标注页码。

4.4.5 多模态融合策略

输入 预处理 抽取 失败兜底
文字 长度校验、NOW 注入 文本模型 无 Key → Mock

三条通道最终都收敛到同一个 Matter 结构和同一套代码约束，前端不需要为不同输入写三套渲染逻辑。

4.5 RAG 与可解释性（A 实现，C 接入）

4.5.1 RAG 架构

材料上传（TXT/MD/PDF）
  → 文本切片（按长度 + 重叠）
  → 片段编号（file_xxx_c1 / doc_pdf_1_p1_c1）
  → 检索打分（中文二元组 + 词频覆盖 + 连续字串 LCS）
  → Top-K 片段组装上下文
  → LLM 回答（必须附出处）
  → 无依据：直接拒答，不调用模型编造

A 侧负责 NotificationRetriever 检索器、打分、ask_question_with_rag、source_ref / is_suggestion 规则；C 侧负责材料上传/存储、/api/files、/api/ask、/api/evidence 接口接入。

4.5.2 切片、编号与检索打分

  • 片段带唯一编号、文件名、页码（如有）、char_start/char_end；
  • 检索前先做中文二元组、英文/数字词、停用词过滤；
  • 打分综合三部分：词项覆盖率、词项权重、连续字串匹配（LCS）加分，低于阈值不返回；
  • 返回 Top-K（默认 3–5）片段，前端展示文件名、片段号、匹配度。

当前是词法检索，不是向量检索。优点是零额外服务、可解释、演示稳定；缺点是同义改写、跨段落归纳召回弱，已列入 P2 的向量检索 + 重排。

4.5.3 生成、出处与拒答

RAG_QA_PROMPT 强制：

  1. 回答 100% 来自检索片段，不使用外部常识；
  2. 每条结论附 【出处：文件名 - 片段ID（第X页）】；
  3. 检索为空时输出“【未找到依据】现有材料中未提及……”，不调用模型补答；
  4. 多项要求分点回答，简练易读。

4.5.4 可解释性：source_ref 与系统建议

Matter 里每条材料/步骤/待办/截止/预警/要点都可以带 source_ref.quote。/api/evidence 返回原文依据；没有原文引用的条目标 is_suggestion=true，前端用黄色“系统建议（无原文依据）”展示。这样用户能区分“通知明确要求”和“AI 补充建议”，而不是把所有内容混成一段看似权威的总结。

4.6 缺项判断与状态推演（A 规则 + C 接口）

4.6.1 三类核对结果

/api/check 的输入是 Matter + 用户勾选 + 用户自述，输出不是简单的“缺/不缺”，而是：

类别 含义 例子
missing_required 原文明确要求、用户未勾选的必交材料 成绩单、身份证复印件
missing_optional 原文标为可选、用户未勾选 获奖证明（选填）
unchecked_unspecified / need_confirm 原文没写清是否必交，或截止时间缺失 “材料是否必交”“截止时间待确认”
profile_issues 用户自述情况与原文要求冲突 原文要视频，用户说“没有”

同时输出 ready、ready_ratio 和一句话结论，前端直接展示“还缺 2 项必交材料：成绩单、身份证复印件”。

4.6.2 状态推演规则

用户勾选材料或完成某一步后，系统不是简单地把所有相关项都打勾，而是按下面的规则推演：

  1. 材料 → 待办联动：材料 prepared 后，只把非交付类、且依赖该材料的待办置为 completed；
  2. 交付动作防误勾：包含“提交/发送/上交/上传/打包/初审/审核/盖章”的动作，即使材料齐了也不自动完成，必须用户明确确认；
  3. 依赖链回填：若后续步骤完成，且它与前置步骤是明确的顺序依赖，则沿链把前置材料标记为已准备；并行分支互不影响；
  4. 代码层兜底：模型输出漂移时，_merge_ai_output 以原结构为基准只吸收状态字段，_fix_todo_actions / _fix_step_titles 补空字段，_code_level_fallback 完成基础联动；
  5. 缺项重建：每次状态变化后重新计算 missing_items，只保留仍缺失的必填材料。

4.6.3 为什么不让模型直接改整份清单

模型适合判断“这句话是什么意思”，不适合保证“ID 不变、顺序不乱、旧字段不丢”。因此状态更新采用“模型只改状态、代码保留结构”的方式：模型返回的 materials/step_list/todo_list 只吸收 status / status_desc，其余字段以原 Matter 为准。即使模型漏返回某个列表，用户已保存的清单也不会被清空。

4.7 Agent 工作流与工具调用（A 实现）

4.7.1 受控 Agent，而不是全自动 Agent

本项目采用受控 Agent 工作流：

  • 模型负责理解意图、选择是否调用工具；
  • 代码负责执行工具、校验参数、兜底；
  • 用户在关键动作（覆盖清单、删除材料、保存新版本）上确认。

这样做的原因是办事场景对“误操作”的容忍度很低：自动帮用户删掉材料、改掉截止时间，比“多问一句”风险大得多。我们把自主性限制在“信息整理”和“建议”层，把写操作交给用户确认。

4.7.2 工具清单

工具/能力 触发场景 输入 输出
check_date 清单有截止时间，需要核对星期/距今/周末 due_at、可选 now 剩余天数、星期、是否周末、风险等级、建议完成时间
补充通知对比 用户上传同一事项的原通知 + 补充通知 两份 Matter + 原文 changes、affected_todos、confirmation_needed、preview_todo_list
查看依据 用户点击某条要求的“出处” Matter + 目标类型/ID 原文片段；无依据标系统建议
准备清单 解析完成后生成待办 Matter + 已勾选材料 todo_list、missing_items、summary

  → 模型返回 tool_calls（name + arguments）
  → 代码执行 check_date / compare
  → 工具结果以 role=tool 回传模型

  → 写入 date_check / suggestions / tool_trace
  → 前端展示“真实调用结果”

没有 Key 时不会假装“模型调用了工具”，而是走同一套工具执行轨迹：真实执行 check_date，返回 tool_calls 和 date_check，只是不做模型总结。这样演示的是“工具真的执行了”，不是“模型说它调用了”。

4.7.4 为什么不用 MCP

比赛评分里 MCP / Function Calling 是同一类“工具集成”能力。本项目选择 Function Calling，原因是：

  • 部署简单：不需要额外 MCP Server、进程和协议适配；
  • 工具数量少（日期、对比、依据），Function Calling 足够；
  • 本地可降级：无 Key 时仍能执行工具；
  • 后续可扩展：把 check_date 换成 MCP Server 只需替换工具执行层，不影响 Prompt 和前端。

4.7.5 失败与可观测性

  • 工具参数非法：返回统一错误，不把异常抛给前端；
  • 模型不调用工具：代码层补一次 check_date，保证至少有一次真实执行；
  • 模型调用未知工具：返回“未知工具”，不执行；
  • 每次调用记录 tool_trace（工具名、参数、结果），前端/答辩可展示真实轨迹。

4.8 补充通知变化处理（A 实现）

4.8.1 差异类型

两份通知分别解析为 Matter A / B，对比：

类型 判定 输出
改期 两边都有 due_at 且不同 changed + 旧/新时间
新增材料 B 有、A 没有（名称归一化后） added + 新材料
删除材料 A 有、B 没有 removed；未明确“不再要求”时必须确认
材料类型变化 必填/可选发生变化 changed
新增/删除步骤 步骤标题归一化后对比 added / removed
补充通知没提 某一类字段在 B 中缺失 info，保留原值，不误删

4.8.2 什么时候必须让用户确认

  • 补充通知没有写“以此为准 / 以本通知为准 / 原通知作废 / 替代原通知”，但截止时间冲突；
  • 补充通知没有明确写“取消 / 不再要求 / 无需提交”，但原材料不再出现；
  • 两份通知标题/事项明显不一致（人工判断）。

明确写了“以此为准”时，改期不再重复问“哪份有效”；但保存新清单前仍要用户点一次“确认更新”，这是写操作确认，不是歧义确认。

4.8.3 受影响待办与版本

原 Matter A + 补充 Matter B
  → diff（截止/材料/步骤）
  → affected_todos（新增/删除/更新截止/保留）
  → preview_todo_list（只预览，不写）
  → 用户确认
  → apply：更新 Matter + change_log.before + version+1
  → 未确认：applied=false，原清单不变

change_log.before 保留修改前的 deadline/materials/step_list/todo_list，支持回看；准备清单每次确认保存后版本递增，保留最近 5 版历史。

5. 核心功能实现（后端）

5.1 统一入口与统一管道

  • main.py 负责 CORS、参数校验（空文本 / 超长 10000 字）、multipart 大小与格式校验、统一 {success,data,error} 响应和异常兜底；
  • analysis_pipeline.analyze_with_fallback 负责“真实模型 / 离线 Mock”切换，文本、PDF、图片三条入口共用；
  • 所有接口始终 HTTP 200，前端只判断 success，避免 422/500 直接把页面打崩。

5.2 文字通知 → Matter

输入一段通知文字，先注入 NOW，走 System Prompt + JSON Schema；输出 title/deadline/materials/step_list/todo_list/sources，再经过复杂度重算、字段裁剪、空字段修补和 missing_items 重建。失败时返回统一错误，不返回半截 JSON。

5.3 缺项核对与准备清单

用户勾选材料、填写自述后，/api/check 做确定性差集，输出 missing_required / missing_optional / unchecked_unspecified / need_confirm / profile_issues。/api/prepare-list 把 Matter 转成可执行待办，支持保存、读取、修改、版本历史和导出。每次确认保存 version 递增，previous_todo_list 与最近 5 版 history 留档。

5.4 查看依据

/api/evidence 接收 Matter + 目标类型/ID，返回 source_ref.quote；没有引用的条目标 is_suggestion=true。前端以弹窗展示原文，黄色标签区分“系统建议”。这让“模型说的”与“通知原文写的”在界面上可区分。

5.5 材料库与 RAG 追问

/api/files 上传 TXT/MD/PDF，切片并编号；/api/files/search 做词法检索；/api/ask 先检索再回答，附文件名、片段号、页码；检索为空时明确拒答。无 Key 时直接返回最相关原文与出处，不让页面卡死。

5.6 补充通知对比与确认

/api/compare 分别解析两份通知并保留文件名/原文/Matter，返回截止、材料、步骤差异和受影响待办。前端展示原要求/新要求/变化；未确认时只预览，确认后才写入新清单，并保留 change_log.before。

5.7 日期核对与导出

/api/tools/check-date 返回星期、距今、周末、常见法定节假日与“是否工作日”，调休提示人工确认；/api/prepare-list/{id}/export 支持 CSV（UTF-8 BOM，Excel 打开不乱码）与 Markdown。日期工具也被 AI 以 Function Calling 方式调用，结果写入 date_check / suggestions / tool_trace。

5.8 会话隔离、限流与删除

前端通过 X-Session-Id 区分浏览器会话，文件库、准备清单、通知对比互不可见；三类数据均提供删除接口。真实模型模式默认按 IP + 路径限流（普通 60 次/分钟、上传 10 次/分钟），Key 只从环境变量读取，不进入仓库。

7. 创新点

7.1 技术创新

  1. 公式化复杂度判定 + 字段裁剪：不让模型"凭感觉"给分，服务端用固定公式重算 complexity_score，并按模式强制裁剪字段，保证同一份通知的输出稳定、可复现。
  2. 三档结构自适应：simple / standard / complex 按需输出，前端只渲染 enabled_sections 中声明的区块，避免"简单通知给一堆空模块"。
  3. 全链路降级：视觉大模型不可用 → 本地 OCR（RapidOCR）→ 离线 Mock；文本模型不可用 → 离线抽取。演示与前端联调不会因为 Key/网络中断而白屏。
  4. 可解释与防幻觉：字段级 source_ref + "查看依据"接口；无原文依据的条目标为"系统建议"；材料库检索不到时直接回答"未找到依据"，不编造。
  5. 受控 Agent + Function Calling：模型负责选择工具，代码执行 check_date/对比，用户确认写操作；工具轨迹可展示，避免全自动 Agent 的误操作风险。
  6. 补充通知的“预览—确认—留档”：差异先预览，改期/删材料默认确认，确认后写新版本并保留 change_log.before，解决“通知改版把旧清单冲掉”的痛点。

7.2 应用创新

  1. 从"读通知"到"能执行"：输出不是一段摘要，而是可勾选的材料清单、可排序的步骤、可提醒的 DDL。
  2. 用户情况驱动的缺项核对：把"通知要求"和"用户已有"做差集，直接告诉用户还缺什么、什么需要确认。
  3. 材料库 + 追问：上传多份材料后可以问"视频有什么要求"，答案附文件名与片段编号，形成"办事资料助手"。
  4. 通知改版管理：同一事项多版通知不需要用户自己对照，系统直接列出改期、新增材料、受影响待办。

7.3 交互创新

  • 出处弹窗：点击材料/步骤/待办后的“出处”，直接看原文片段；没有依据的标黄色“系统建议”，不把 AI 补充伪装成原文。
  • 差异预览：补充通知先展示“原要求 / 新要求 / 变化 / 受影响待办”，用户确认后才覆盖，避免“静默修改”。
  • 日期卡片 + 工具轨迹：显示剩余天数、星期、周末/节假日提示，并能在答辩中展示 tool_trace，证明工具真实执行。
  • 材料库追问：回答下方展示文件名、片段编号、匹配度，用户可以判断“这句话是从哪份材料来的”。
