# 技术文档（完整版）

> 本文件覆盖项目背景、技术选型、系统架构、核心算法机制（AI端）、后端实现、测试与部署。可直接导出为 PDF 提交。

## 1. 项目背景与需求概述

### 1.1 项目背景与痛点
在高校与职场中，面对冗长的公文、比赛简章或审批通知，用户往往需要耗费大量时间人工拆解“需要交什么材料”、“何时截止”以及“具体办理流程”。当前的通用大模型（LLM）虽然具备优秀的阅读能力，但在直接应用于此类场景时存在明显缺陷：
1. **信息碎片化**：要求分散在长文各处，人工核对极易漏看。
2. **模型幻觉**：通用大模型容易捏造原文中不存在的规定或要求，导致用户准备错误。
3. **缺乏结构化交互**：纯文本答复无法直接转化为可勾选、可推进的“办事清单”。

### 1.2 核心目标与用户场景
本项目旨在打造一款面向学生、社团内勤、职场人士的**“智能办事清单助手（不漏办）”**。系统通过“文本/图片/PDF输入 → AI解析 → 结构化清单生成 → 状态动态联动”的闭环，实现：
- **精准提取**：将长篇通知转化为结构化的 JSON 清单。
- **防幻觉溯源**：每一条要求必须绑定原文，没有依据的标为“系统建议”。
- **动态缺项核对**：根据用户勾选，实时推演前置/后置任务，高亮缺失项。
- **DDL 提醒**：自动识别截止时间并生成提醒调度任务。

## 2. 技术选型

结合“快速响应、高准确率、易降级演示”的项目需求，本系统的技术选型如下：

### 2.1 后端与开发语言
- **语言**：`Python 3.10+`。拥有最完善的 AI 与文档处理生态。
- **Web 框架**：`FastAPI + Uvicorn`。天然支持异步与类型提示，极适合处理大模型耗时的流式请求、多文件上传与跨域配置。
- **数据校验**：`jsonschema`。针对大模型输出的结构进行严格校验，防止脏数据击穿前端。

### 2.2 AI 大模型引擎
- **接口标准**：`OpenAI 兼容接口`。系统不绑定单一供应商，支持灵活配置 OneAPI 中转站、DeepSeek、通义千问等国内外模型，保证网络与额度的可用性。
- **双引擎架构**：采用“大模型语义理解 + 纯代码逻辑约束”双引擎，模型负责“读懂”，代码（如复杂度公式重算、字段互斥裁剪）负责“规训”。

### 2.3 文档解析与多模态
- **PDF 引擎**：`pymupdf` / `pypdf`。采用双引擎互为兜底，保障文字型 PDF 的稳定提取。
- **图片 OCR**：视觉大模型（如 GPT-4o）结合本地开源 `RapidOCR`。当大模型接口不可用时，自动降级为本地 OCR，确保功能不中断。

### 2.4 存储与前端交互
- **存储层**：轻量级 JSON 原子写。由于系统定位为会话式信息整理工具，为降低部署成本，采用本地线程锁+临时文件原子写保障状态持久化，无需额外部署数据库。
- **前端渲染**：支持 HTML/CSS/JS 或 Vue/React，基于 `enabled_sections` 实现三栏（输入区、清单区、原文预览区）联动响应式渲染。

## 1. 项目概述

**问题背景**：校园与职场中的"办事通知"以纯文字、截图、PDF 等形式散落在群消息和公告里，关键信息（截止时间、材料清单、办理步骤、审核要求）分散在长文中。人工阅读容易漏材料、看错时间、混淆流程；通用大模型直接回答又容易编造，用户无法核验。

**一句话价值**：把一段通知变成**可勾选、可溯源、可提醒**的待办清单。

**目标用户**：在校学生（奖助学金、竞赛报名、证件办理）、社团/单位内勤（活动立项、经费报销、场地申请）、职场人士（入职材料、资质办理、行政审批）。

**本期范围（P1）**：文字通知解析、截图识别、文字型 PDF 提取、三档结构化输出、材料清单与缺项核对、查看依据、材料库检索与追问、清单保存与恢复。
**后续规划（P2）**：多文件合并解析、复杂条件分支、日历同步、多人协作。

### 2.1 典型场景

- 学生收到一条奖学金通知：需要知道**截止时间**、要交**哪些材料**、**交给谁/交到哪**、**先做什么后做什么**。

## 4. 核心算法与机制

### 4.1 大模型状态推演与动态缺项联动机制

本项目并未采用传统的死板规则做状态联动，而是创新性地引入了**“基于大模型常识推理 + 代码层兜底”**的双引擎状态推演机制。

- **交付动作防误勾**：通过严格的语义识别（如“提交、上传、打包、初审”等关键词），确保即使前置材料已齐备，系统也不会将“交付动作”误标记为完成，必须由用户显式操作。
- **顺序与并行常识倒推**：若用户在清单中完成了后续的“录制视频”步骤，系统利用图依赖（DAG）与常识推理，自动沿链式向前回填，将前置的“提交初审”与“准备材料”一并标记为完成。
- **代码层硬核兜底**：针对大模型可能出现的输出漂移，代码层实现了空标题（`_fix_step_titles`）与空待办（`_fix_todo_actions`）的强行补全；一旦大模型宕机，纯代码的 `_code_level_fallback` 依然能完成基础的非交付类步骤联动。

### 4.2 基于 RAG 检索增强的防幻觉与原文溯源机制

为了彻底解决大模型在长文本问答中的“胡编乱造”问题，本项目实现了完整的多阶段 RAG（检索增强生成）流程：

1. **多材料切片与编号（Chunking）**：自研 `NotificationRetriever` 引擎，支持按标点与长度对通知进行无损切片，每个片段自带唯一编号（如 `doc_pdf_1_p1_c1`）、来源文件名与页码。
2. **混合相关性打分**：结合词频覆盖度、连续字串匹配度（LCS 相似度加分）与实体关键词加权，在多份材料中精准定位 Top-K 相关原文。
3. **先查材料，再回答**：将检索到的原文片段组装后喂给大模型，强制大模型在回答末尾附上出处 `【出处：文件名 - 片段ID】`。
4. **无依据拦截与降级兜底**：若本地检索未命中（材料外问题），系统直接拦截并返回“未找到依据”；若大模型 API 突发欠费或宕机，系统自动降级为纯本地检索展示，直接抛出最相关的原文片段与出处，确保服务永不宕机、绝不瞎编。

### 4.3 输出稳定性与结构化解析

1. **复杂度重算**：不采信模型给的分数，用固定公式 `0.2·deadline + 0.1·多提醒 + 0.2·多步骤 + 0.2·材料 + 0.1·审核 + 0.1·依赖 + 0.1·周期 + 0.1·子步骤`，再按 `has_sub_steps/has_review/has_dependencies → complex`、`<0.3 simple`、`0.3–0.6 standard`、`>0.6 complex` 判定。

## 7. 创新点

### 7.1 技术创新

1. **公式化复杂度判定 + 字段裁剪**：不让模型"凭感觉"给分，服务端用固定公式重算 complexity_score，并按模式强制裁剪字段，保证同一份通知的输出稳定、可复现。
2. **三档结构自适应**：simple / standard / complex 按需输出，前端只渲染 `enabled_sections` 中声明的区块，避免"简单通知给一堆空模块"。
3. **全链路降级**：视觉大模型不可用 → 本地 OCR（RapidOCR）→ 离线 Mock；文本模型不可用 → 离线抽取。演示与前端联调不会因为 Key/网络中断而白屏。
4. **可解释与防幻觉**：字段级 `source_ref` + "查看依据"接口；无原文依据的条目标为"系统建议"；材料库检索不到时直接回答"未找到依据"，不编造。

### 7.2 应用创新

1. **从"读通知"到"能执行"**：输出不是一段摘要，而是可勾选的材料清单、可排序的步骤、可提醒的 DDL。
2. **用户情况驱动的缺项核对**：把"通知要求"和"用户已有"做差集，直接告诉用户还缺什么、什么需要确认。
3. **材料库 + 追问**：上传多份材料后可以问"视频有什么要求"，答案附文件名与片段编号，形成"办事资料助手"。

## 8. 总结与展望

**已完成**：文字/截图/PDF 三种输入通道；三档结构化输出；材料清单与缺项核对；查看依据；材料库片段检索与追问；准备清单保存与恢复；8 套自动化测试与一键自检；Docker 部署方案与演示素材。

**局限**：扫描版 PDF 依赖截图通道；复杂表格/手写体的识别精度取决于模型；无团队 Key 时为演示数据（结构真实、内容虚构）。

**展望**：多文件合并解析、复杂条件分支（"若为应届生需额外提交…"）、日历/飞书同步、多人协作清单。
